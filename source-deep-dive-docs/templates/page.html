NN 页面标题

这页回答一个问题：XX 是怎么做到的、为什么这么做。读完你能说出它的三个关键取舍。

学习目标

  • 能说出 XX 的职责边界，以及它不做什么；
  • 能画出一次 XX 的完整调用路径，并指出每一步的源码位置；
  • 能判断某个改动会不会破坏 XX 的约束（列举约束与它们的落点）；
  • 知道 XX 出错时的现象，以及从哪一行代码能确认原因。

1. 第一个子问题

结论：XX 的顺序是「先 A、再 B、最后 C」，前两步任一命中即返回，后面的不再执行。

path/to/SomeClass.java:180-206
private Decision decide(Request request) {
    // 显式拒绝优先级最高：命中即返回，不再往下走
    Decision denied = explicitDeny(request);
    if (denied != null) {
        return denied;
    }
    Decision allowed = explicitAllow(request);
    if (allowed != null) {
        return allowed;
    }
    // 插件故障时取「拒绝」而不是「允许」：故障不应扩大权限
    return pluginFailed() ? Decision.deny() : policyDefault(request);
}
步做什么要点
①查显式拒绝优先级最高，命中即返回
②查显式允许只有显式拒绝未命中时才看它
③看策略默认除非插件故障，故障一律取拒绝
为什么故障时取「拒绝」而不是「允许」

替代方案是把故障当作「无策略」从而放行——实现更简单，也不会因为插件崩了就让用户寸步难行。

放弃它的原因是故障方向必须是安全方向：插件崩溃往往伴随状态不可信， 此时放行等于把「插件坏了」转换成「权限被绕过」，而后者不会产生任何报错。 取拒绝则失败可见，用户能立刻发现并处理。依据：SomeClass.java:198-204 的注释 与该处直接返回拒绝的实现。
