# 阶段④ 核验：四道关

核验不是「写完后检查一下」，它是工序的一部分：**每改一页就跑一次**。核验不通过的文档不算完成。

```
① 引用核验    脚本    每条 file:line 都落到源码上          → 零缺文件、零越界、歧义清零
② 一致性核验  脚本    编号 / 侧栏 / 翻页 / 链接互相对得上    → 零不一致
③ 渲染核验    人工    断网打开仍然可读、图有降级            → 能看见、能跳转、能复制
④ 内容核验    人工    引用对不对得上下文                    → 抽查通过率 100%
```

前两关必须自动化，后两关必须人工——**它们各自能抓到对方抓不到的问题**。

---

## 为什么必须用脚本

这套文档里有**几百到几千条 `file:line` 引用**（一个 30 页的文档轻易超过 1500 条）。源码一改动，行号就漂移。靠人眼维护必然出错，而**出错的引用比没有引用更糟**：它让读者以为有证据。

脚本能查的（全部可自动化）：

- 文件是否存在
- 行号是否越界
- 同一个文件名在仓库里有多个候选时必须**报歧义**，而不是静默挑一个
- 引用的那一行是否可疑（空行、只有括号）——大概率说明行号偏了
- 页面编号、侧栏条目、翻页顺序、链接目标是否自洽

脚本**查不了**的（必须人工）：

- 行号对，但引的不是那一段（引错段落）
- 引用内容与正文描述不符
- 代码转义有没有写错（`<` 没转成 `&lt;`）
- 图表能不能渲染、离线能不能看

**最后一条纪律**：「静态检查通过」不等于「能用」。凡是涉及产物能否工作的结论，必须**实际跑一次 / 打开一次**再下判断。

---

## 第一关：引用核验（`verify-refs.sh`）

### 用法

脚本用**本技能自己的那一份**（`<技能目录>/scripts/verify-refs.sh`），**不要复制进产出目录**：
复制出去的副本不会跟着技能升级，只会漂移成两份（见 `SKILL.md`「复用优先于重建」）。
文档目录**显式给**最稳；选项要写在位置参数**前面**（解析到第一个非选项参数就停）。

```sh
# 显式给文档目录 + 源码根（推荐：两个都给，别依赖任何自动探测）
sh <技能目录>/scripts/verify-refs.sh <文档目录> <源码根1> <源码根2>

# 只给文档目录，源码根自动探测
sh <技能目录>/scripts/verify-refs.sh <文档目录>

# 列出「引用注释/注解行」的条目（默认只汇总数量）——选项在前
sh <技能目录>/scripts/verify-refs.sh -v <文档目录>

# 只看某几种扩展名的引用
sh <技能目录>/scripts/verify-refs.sh -x java,ts,go <文档目录>
```

### 关于「自动探测源码根」——它会选错，要知道症状

自动探测的方式是：从文档目录逐级向上，找含 `.git` 或常见构建文件（`pom.xml` / `package.json` / `go.mod` / `Cargo.toml` / `pyproject.toml` …）的目录。

**它会选错的典型布局**：文档自己独立成一个仓库，源码仓库在它旁边。

```
workspace/
├── project/          ← 源码在这里，是文档要引用的对象
├── project-docs/     ← 文档在这里，自己也有 .git
└── ...
```

从 `project-docs/` 向上找，最近的「像仓库」的目录是 `project-docs/` 自己——于是索引里只有文档仓库，**所有引用都变成「缺文件」**。

**症状**：`索引文件数` 明显偏小（比引用条数还少一个数量级），同时「缺文件」上千条。

**怎么办**：显式给出源码根。根可以给多个，按「从具体到宽泛」排列——`verify-refs.sh` 会按顺序用它们解析引用，找不到再退回按路径后缀匹配。

```sh
sh <技能目录>/scripts/verify-refs.sh docs ..            # 源码根 = 上一级
sh <技能目录>/scripts/verify-refs.sh docs . ../other    # 多个根，按顺序试
```

脚本在「缺文件」数量偏多时也会直接把这条提示打出来，不会让你对着上千条报错猜原因。

### 输出怎么读

| 分类 | 含义 | 怎么办 |
|---|---|---|
| **缺文件** | 索引里找不到这个文件 | 路径写错，或文件已删除。**必须修** |
| **越界** | 行号 > 文件总行数 | 源码改过了，引用过期。**必须修** |
| **歧义** | 同名文件有多个候选，脚本无法判定 | 把引用路径补到唯一的一层。**必须修**（不算硬错误，但会把校验落空） |
| **可疑** | 引用的那一行是空行或纯括号 | 行号大概率偏了。逐条确认 |
| **引用注释/注解行** | 首行是注释、注解或 `import` | **属预期**（引注释是常见写法）。默认只计数，需要时 `-v` 列出 |

**退出码**：`0` = 无缺文件、无越界；`1` = 有；`2` = 环境问题（找不到文档或源码根）。

### 修「越界」的正确顺序

**不要**直接把行号改成文件末尾。正确做法：

1. 打开那个文件，找到当初引用的**那段代码现在在哪**
2. 重新确认区间（也许它被挪到了别处，也许被重构了）
3. 顺便检查**正文里对这段代码的描述是否还成立**——源码改动往往意味着行为也变了

**这就是为什么核验要在每次改动后跑**：越界不只是行号问题，它是「源码变了，文档可能过期了」的信号。

### 关于简写引用

形如 `<code>:645</code>`（只给行号、文件名在上文）的引用**无法自动校验**。脚本会报出这类引用的数量。

写文档时**尽量用带文件名的完整引用**。简写只用于同一段里连续引用同一个文件，且要保证上文紧邻处出现过完整引用。

## 第二关：一致性核验（`check-docs.py`）

### 用法

同样用本技能的那一份，并把文档目录**显式给**——脚本不在产出目录里，别指望它自己猜对：

```sh
python3 <技能目录>/scripts/check-docs.py <文档目录>
python3 <技能目录>/scripts/check-docs.py            # 不给则用当前目录
```

它**不需要配置**——所有期望值都从侧栏推导（见下）。

### 检查项

| # | 检查 | 说明 |
|---|---|---|
| 1 | 侧栏条目集合逐页一致 | 顺序与文字全同，且**恰好一个** `aria-current` 指向本页 |
| 2 | 侧栏链接文字编号 = 目标文件编号 | 文字以页号开头时校验 |
| 3 | `<title>` / `<h1>` / 面包屑的编号 = 自己文件名编号 | 三处都要对 |
| 4 | 所有内部链接的落地文件存在 | `href` 指向的 `.html` 必须存在 |
| 5 | `NN 页` 引用指向存在的页号 | 防止改编号后留下死引用 |
| 6 | 图/表编号的前缀 = 本页编号 | 跨页引用只提示（可能是正常的） |
| 7 | 翻页的上一页/下一页与侧栏顺序一致 | 防止插页后漏改 |
| 8 | 页脚与脚本引用齐全 | 每页都引了 `assets/app.js` 等 |

**为什么从侧栏推导**：侧栏是「本页集合」的自然声明处，写在每个页面里。从它推导意味着**不需要维护第二份页面清单**——也就不会出现「清单和实际页面不一致」。新增一页时，只要把它加进侧栏，核验脚本立刻能发现漏改的地方。

**退出码**：`0` = 全部一致；`1` = 有错误；`2` = 环境问题。

## 第三关：渲染核验（人工，5 分钟）

**在真实的浏览器里打开，而不是看源码。** 而且必须**两种条件都试**：

### A. 联网
- 页面能打开、样式正常
- 代码有语法高亮、每行左侧有行号
- 图渲染成图形（不是一串源码）
- 点行号能复制该行的锚点链接；点「复制」按钮能复制代码（**且不带行号**）
- 侧栏搜索能过滤
- 翻页能走完一圈（从第一页到最后一页再回到首页）

### B. 断网 / 缺本地库（**这条最容易被漏**）
- 依然能读、能跳转、能看代码（高亮可以没有）
- **图降级为源码显示**，且页面顶部有明确说明（而不是留一片空白）
- 不出现「半截渲染」或脚本报错导致的空白页

**为什么要专门测断网**：文档的价值之一是离线可读。而「本地库缺失 + CDN 也取不到」是很容易发生的组合（见 `05-pitfalls.md` 第 4、5 条）。**只测联网的一条路，等于没测。**

### C. 双击打开（`file://` 协议）
- 用 `file://` 打开和用 HTTP 服务打开表现必须一致
- 如果某个功能依赖 `fetch` / XHR / 模块导入，它在 `file://` 下会失败——**这就是为什么要避免这类方案**

## 第四关：内容核验（人工抽查）

**抽多少**：全部引用的 **10%**，且**必须覆盖每一页**（每页至少抽 2 条）。

**怎么抽**：不要只抽你最有把握的那些。优先抽：

- 你自己写的时候就觉得「大概是这样吧」的
- 数字类论断（上限、默认值、超时、条数）
- 「必须 / 不能 / 永远」这类绝对化表述
- 涉及失败路径的论断（「校验失败时返回空」）
- `callout design` 里的因果推理（「因为 A 所以选 B」）

**怎么查**：打开源码**读上下文**，而不只是核对行号对不对。要回答三个问题：

1. 这一行/这一段，真的说的是我写的那个意思吗？
2. 这个论断有没有**例外情况**没被我写进去？
3. 我引的是「实现」还是「注释」？如果只是注释，实现真的和注释一致吗？

**发现不一致时**：改文档，并在正文里**明确写出源码的实际行为**。如果注释与实现不符，那本身就是值得写进文档的一条（读者最需要知道「哪里和说明不一样」）。

**通过标准**：抽查条目的正确率 **100%**。有一条错，说明该页的引用方式有系统性问题，要**整页复查**而不是只改那一条。

## 什么时候跑

| 时机 | 跑什么 |
|---|---|
| 写完一页 | 第一、二关 |
| 批量改动（重编号 / 改导航 / 移动目录） | 第一、二、三关，**全部** |
| 目标仓库的源码有改动 | 第一关（然后把新出现的越界逐条回源码确认） |
| 交付前 | 四关全跑 + 更新页脚里的「本页依据」 |
| 纳入自动化（可选但推荐） | 第一、二关接进 CI 或提交前钩子 |

**推荐接进自动化**的理由：这两关是确定性的、不需要人判断的。一旦接进去，「引用过期」就再也不会悄悄积累。
