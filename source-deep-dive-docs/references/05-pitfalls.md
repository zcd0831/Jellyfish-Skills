# 通用坑点清单

每条按「**现象 → 原因 → 怎么做**」写，都是实际踩过并验证过的。做批量修改前请先扫一遍 A 组。

---

## A. 批量文本操作（改编号、替换、重命名）

### 1. 批量改编号会互相碰撞，必须两段式

**现象**：把 28 个页面重新编号后，发现有的页面编号被改了两次，指向了错误的地方。

**原因**：旧号恰好是新号。例如「旧 25 → 新 21」和「旧 17 → 新 08」，如果按顺序逐条替换，一条规则的输出会被后一条规则再次命中。

**怎么做**：**两段式 + 占位符**。

```
第一段：把所有待改文本替换成不含数字的唯一占位符，并记下 占位符 → 新值
第二段：全部规则跑完后，统一把占位符还原成新值
```

占位符必须**不含数字**（含数字会被后续规则再匹配一次）。用一个源码里不可能出现的字符序列，例如 `\x00` + 字母 + `\x00`。

```
遍历时：  "25 页"  →  "\x00a\x00"
全部跑完： "\x00a\x00" → "21 页"
```

**检查方法**：改完后再跑一遍「有没有旧编号残留」的检查（用旧号集合反查全文），零残留才算过。

### 2. 规则之间有先后顺序，顺序错了会吃掉内容

**现象**：区间 `22–27 页` 被改成了 `18–21 页`（只对了前半段）。

**原因**：处理「区间」的规则和处理「`NN 页`」的规则都能匹配这个串。先跑的规则把后半段吃掉了，后跑的就看不到完整区间。

**怎么做**：**范围更大、更具体的规则必须排在更宽泛的规则之前**。以改编号为例，安全顺序是：

```
① href / 文件名          （最具体，先做）
② 链接文字里的编号
③ 图 / 表编号（形如 图 03-2）
④ 编号区间（NN–MM）      ← 必须在 ⑤ 之前
⑤ 「NN 页」这类页码引用
⑥ 本页自己的编号（title / h1 / 面包屑）
```

**通用原则**：把规则按「匹配的具体程度」从高到低排序，且**每做一处替换就立刻用占位符保护起来**，避免被后续规则再命中。

### 3. 批量替换一定会误伤，必须加边界

**现象**：改页码的同时，把 `JDK 17` 改成了 `JDK 08`，把行号 `:20` 改成了 `:11`，把 `≈25 fps` 改成了 `≈21 fps`。

**原因**：两位数在文本里到处都是——版本号、行号、帧率、数量、区间、列宽、年份。

**怎么做**：

- **加前后边界**：正则里用「前一个字符不是数字」和「后一个字符不是数字」把匹配夹住，`(?<!\d)(\d\d) 页(?!\d)`
- **绑定上下文**：不要裸匹配 `\d\d`，而是匹配「编号出现时必然伴随的那些词」——` 页`、`图 `、`表 `、`href="`、`–`
- **先列出再决定**：批量修改一律**先 dry-run**，把「将被改动的每一处」连同上下文打印出来，人工扫一遍再 `--apply`
- **改完做残留检查**：用旧值集合反查全文，逐个确认每处残留都是「不该改的」（如 `JDK 17`）

### 4. 脚本能匹配的模式总是比你以为的少

**现象**：以为自己覆盖全了，结果有三类引用没被改到：图表内部的节点标签、散文里的「第 15/16 两页」、以及 `<a>28</a>` 这种裸数字链接文字。

**原因**：凡是「数字出现在非结构化位置」的地方，基于模式的替换都覆盖不到。

**怎么做**：改完后**不要只看脚本报告**，另做一个独立检查：

- 用旧号集合反查全文（找残留）
- 用新号集合反查，确认每一处新号都是「被改出来的」而不是「本来就是这个数字」
- **抽 3~5 页人工通读一遍**，尤其看图和散文

**这条的通用版**：自动化能覆盖 90%，剩下的 10% 必须人眼——而且要**专门去找漏网的**，不是随便翻翻。

## B. 引用与行号

### 5. 同名文件会让引用校验静默落空

**现象**：核验脚本报好几处「行号可疑」，但打开文件看明明是对的。

**原因**：仓库里有多个同名文件（`PluginConfig.java` 有 6 个、`pom.xml` 有十几个）。脚本按文件名后缀匹配时**取到了另一个同名文件**，于是报出假的错误。

**怎么做**：

- 核验脚本遇到多候选时必须**报「歧义」而不是静默取第一个**——静默取第一个会把错误伪装成通过
- 写引用时把路径补到能唯一确定的那一层（从模块/包名开始）
- 歧义条目要逐条修：它虽然不算硬错误，但它意味着**这条引用根本没被校验**

### 6. 行号引用是最脆弱的资产

**现象**：隔了一段时间再看，几百条引用里有一批行号已经指向别的代码了。

**原因**：行号随任何一次编辑漂移——加一行注释、删一个空行、格式化，全部会偏。

**怎么做**：

- **优先引「不易动」的位置**：方法签名、类声明、常量、完整的控制流块。避开文件末尾、单行括号、紧凑的 getter
- **引区间而不是单行**：区间起点偏个一两行通常还在同一段里，单行偏了就完全错了
- **把核验脚本放进流程**：每次源码改动后跑一次，让漂移当场暴露而不是积累
- **接受它会过期**，并在文档的页脚写清依据的版本/时间点，方便读者判断

### 7. 「不是引用」的文字会被核验脚本当成引用

有两类文字最容易踩：**引注释原文**，以及**正文里的示例**。

**现象一**：核验报告里出现一批「首行是注释行」的条目，看起来像错误。

**原因**：引用 javadoc 原文（解释设计意图的段落）是**常见且正确**的写法，但它会让自动化判据报警。

**怎么做**：核验脚本把这类单独归类、**默认只汇总数量**（加 `-v` 才列出），避免噪声淹没真问题。写引用时在出处行注明「（类注释，解释为什么……）」，让读者知道这是注释而非代码。

**现象二**：解释「什么叫歧义」时写了「引用若只写到文件名（如 `README.md:27`）」，结果核验脚本把**这个示例本身**抽出来当引用去校验，报出一条缺文件或歧义。

**原因**：核验脚本靠正则抽取，它不区分「真引用」和「长得像引用的示例」。示例里带的文件名与行号，恰好就是它要找的模式。

**怎么做**：

- 示例用**占位名**，例如 `同名文件.md:27`、`路径/文件.ext:123` —— 占位名不在仓库里存在，也不会被模式命中成真引用。
- 或者改写措辞避开「文件名 + `:` + 行号」的形状（例如「只写到文件名、不带路径的那种引用」）。
- **改完一定要重跑核验**：这类污染只有跑一遍才会暴露，而且它常常伪装成「文档里真有一处引用错了」。
- 这条的通用版：**凡是「解释工具行为」的文档，都要检查示例文本会不会被工具自己吃掉。**

## C. 前端资产与离线可用

### 8. 前端库选错包：给打包器用的版本在浏览器里直接报错

**现象**：代码高亮始终不生效，控制台报 `require is not defined`。

**原因**：同一个库常在 npm 上有**两个包**：

| 包 | 内容 | 浏览器能否直接用 |
|---|---|---|
| 主包（如 `highlight.js`） | `lib/*.js` 是 **CommonJS 模块**，给打包器用 | ✗ 含 `require(...)`，浏览器报错 |
| CDN 构建包（如 `@highlightjs/cdn-assets`） | 预构建的浏览器 bundle | ✓ |

**怎么做**：

- 优先用名字里带 `cdn` / `dist` / `browser` / `umd` 的那个包，或直接取官方 CDN 的 URL
- **下载后必须实际加载一次验证**：在浏览器环境里检查全局对象是否存在、关键函数是否是函数
- **看文件大小**：KB 级（几 KB）的「压缩后库」几乎肯定是错误页或模块壳。一个正常的前端库 bundle 通常是几十 KB 到几 MB
- 若自己写了获取脚本（见第 14 条），在脚本里加**体积下限校验**，太小的直接报错，而不是静默装上一个坏文件

### 9. 「本地优先 + CDN 兜底」的两条路都要分别验证

**现象**：以为有 CDN 兜底就没问题，实际上**本地文件缺失 + CDN 地址也是错的**，两档同时失效，功能彻底不可用。

**原因**：只测了一条路。CDN 的 URL 是从别处抄来的，没验证过；本地文件因为体积可疑（见上条），其实是个坏文件。

**怎么做**：

- 两条路都要**实际测**：本地文件在 → 用本地；本地文件移除 → 应当走 CDN 成功
- 再加第三种情况：**两者都不可用** → 必须**优雅降级**（图显示源码、代码不高亮但仍可读、页面顶部给出说明），而不是留一片空白
- 兜底逻辑本身要能看见结果：降级时给用户一条明确的提示（缺什么、怎么补）

### 10. `file://` 打开时，`fetch` / XHR / ES module 会被拦

**现象**：本地双击打开，导航栏是空的、样式没生效。

**原因**：浏览器对 `file://` 协议有 CORS 限制，`fetch` / `XMLHttpRequest` / `import` 都会失败。任何「用 JS 动态加载导航 / 样式 / 片段」的方案在这里都会挂。

**怎么做**：

- **能内联就内联**：导航（侧栏）、样式、脚本直接写进每个页面 / 用相对路径 `<link>`、`<script src>`
- `<link rel="stylesheet">` 和 `<script src="...">` 用**相对路径**在 `file://` 下是正常的，可以放心用
- 避免 `fetch` 加载 JSON 配置、避免 ES module 的 `import`（改用一个 IIFE 的传统脚本）
- 交付前**用 `file://` 双击打开测一遍**，而不是只测本地 HTTP 服务

## D. 一致性与维护

### 11. 一致性靠人眼维护必然失效

**现象**：插了一页之后，有的页面侧栏没加、有的翻页没改、有的编号忘了更新。

**原因**：同一个事实（「有哪些页面、什么顺序」）被复制到了 N 个文件的多个位置（侧栏、翻页、首页卡片、正文引用）。N 大了以后人手必然漏。

**怎么做**：

- 把「有哪些页面」的**声明处收敛到一处**（侧栏），其他地方由脚本核对
- 用核验脚本检查所有派生位置的一致性（见 `04-verification.md` 第二关）
- **批量操作后必须全量核验**，而不是只检查你「改过的地方」——漏掉的地方恰恰是你没想到的地方

### 12. 两套资产必然漂移

**现象**：样式表有两份（文档站一份、工具模板一份），改了一份另一份没改，两边慢慢长得不一样。

**原因**：复制资产容易，同步难。

**怎么做**：

- **复用优先**：目标仓库已有同类资产就复用它，不要另起一套
- 必须有第二份时，**明确哪一份是权威**，并在另一份的头部注释里写清「这份是副本，权威版本在 X」
- 参考实现与产物要分清去向：`templates/`（页面骨架、`style.css`、`app.js`）复制过去后就成为产物的一部分，此后按产物维护；`scripts/`（核验脚本）**永远不复制**，始终从技能目录调用——复制出去的那份没人会同步，而核验脚本的价值全在「跑的就是最新那一版」

### 13. 临时文件会残留

**现象**：工作目录里攒了一堆 `.tmp-*.py`、`*-tmp.sh`，或者核验脚本每次运行都留下几个临时文件。

**原因**：清理逻辑只删了「一个」临时文件，而实际创建了三个。

**怎么做**：

- **用一个统一的临时名前缀**（含 PID），把该次运行产生的所有临时文件都挂在这个前缀下，一次删净
- 用 `trap` 在退出 / 中断时清理，覆盖 `0 1 2 3 15` 这些信号
- 临时文件放系统临时目录（`$TMPDIR` / `/tmp`），不要放在版本库目录里
- 工作用的探针脚本**先放临时目录**，只有确认要长期保留才移进仓库

## E. 交付与仓库卫生

### 14. 第三方大文件不要进版本库

**现象**：为了「离线自包含」，把几 MB 的前端库 bundle 提交进去，仓库体积暴涨，以后每次升级都产生巨大 diff。

**默认做法：根本不交付这两个库。** 它们对文档不是必需品——缺库时 `app.js` 先回退 CDN，再不行就降级
（代码不着色、图以源码形式展示并给出提示），页面照样能读。所以产出目录里只留页面与前端资产，
放不放 `vendor/` 由读者自己决定；放本地时要让版本与 `app.js` 里 CDN 兜底的一致。

**真需要「开箱即用、不联网」时**（内网机器、交付给外部、归档）：

- 加获取脚本 + 忽略规则：脚本按确定的 URL 与版本号下载，文件写进 `.gitignore`
- 这个脚本属于**目标仓库自己的资产**，随目标仓库维护——它不是技能提供的默认产物，别指望下次还给你生成一份
- 脚本要**校验下载结果**（体积下限 + 内容特征），失败时明确报错：下载到一个 HTML 错误页是最常见的坑
- 或者干脆把产物打进一个归档包发布，而不是塞进版本库

### 15. 编辑器 / 系统文件会混进提交

**现象**：`.DS_Store`、`.idea/`、`*.iml`、`*_files/` 出现在待提交列表里。

**怎么做**：项目根建 `.gitignore`，至少覆盖：

```gitignore
.DS_Store
**/.DS_Store
.idea/
.vscode/
*.iml
*.swp
*~
.#*
# 浏览器「另存为整页」产生的伴随目录
*_files/
```

**注意**：多仓库工作区里，`.gitignore` 要建在**每个实际是 git 仓库的子目录**里——在非仓库的父目录建了不生效。

## F. 工具与环境

### 16. 把复杂文本处理放进脚本文件，不要塞进一行命令

**现象**：一条很长的 `grep | sed | awk` 管道在某个环境里报一堆奇怪的语法错误，或者被判定为非法命令。

**原因**：不同环境的 shell 不一样（POSIX `sh` / `dash` / `bash` / `zsh`），很多写法并不通用：

- `VAR=value cmd` 前缀赋值不是所有环境都支持
- `cmd 2>&1` 在某些受限终端里会被拆坏
- 花括号展开 `{a,b}`、`[[ ]]`、数组、`<<<` 是 bash/zsh 扩展，`dash` 里没有
- `sed -i` 的语法在 GNU 与 BSD 上不同（后者要求 `-i ''`）

**怎么做**：

- 超过两三个管道、或涉及引号嵌套的，**写进 `.sh` 文件再 `sh file.sh` 执行**——脚本文件里可以用完整语法，也便于阅读与复用
- 脚本顶部用 `#!/bin/sh` + **只用 POSIX 语法**，可移植性最好
- 需要更强文本处理时用专门的脚本语言（Python 等），而不是硬凑 shell

### 17. 变量名后紧邻多字节字符要写 `${var}`

**现象**：脚本里 `"${prefix}中文"` 之类写法在某个 locale 下报 `unbound variable` 并中止。

**原因**：某些 shell 在非 UTF-8 locale 下，会把紧跟变量名之后的多字节字符的首字节吃进变量名。

**怎么做**：**所有变量展开一律写成 `${var}` 形式**，不要写 `$var` 后紧跟中文字符。同时脚本里避免 `set -u` 与未定义变量的组合，或者在头部显式给默认值。

### 18. 变量名与保留字

**现象**：用 `status`、`path`、`lines` 之类的名字在某个 shell 里行为异常。

**怎么做**：脚本里用带前缀的自定义变量名（`DOC_`、`SRC_`、`TMP_`），避开 `PATH`、`IFS`、`HOME`、`PWD`、`status`、`command` 等常见保留/特殊名字。

### 19. 「静态检查通过」不等于「能跑」

**现象**：脚本语法检查通过、JS 花括号配对、函数都定义了——交付后发现功能根本没生效（见第 8 条）。

**原因**：静态检查只能发现「写错了语法」，发现不了「引用了一个不存在的包」「CDN 地址是 404」「返回的是错误页」。

**怎么做**：

- 凡是涉及「产物能不能用」的结论，**必须实际加载 / 运行一次**再下判断
- 对前端资产：在浏览器（或等价的 JS 运行时）里加载，检查全局对象与关键函数
- 对脚本：用一个真实输入跑一遍，看输出与退出码
- **报告结论时区分「检查了什么」**：说「语法检查通过」而不是「已验证可用」

### 20. 核验工具配置错了，会伪装成「文档全错」

**现象**：跑引用核验，报出上千条「缺文件」，结论是「文档烂了」——但文档其实只有个别问题。

**原因**：核验脚本的**源码根选错了**，索引里几乎什么都没有，于是每一条引用都找不到。

最典型的布局：文档自己独立成一个 git 仓库，源码仓库在它旁边。脚本「从文档目录向上找最近的仓库根」会停在文档仓库上，压根看不到源码。

**怎么做**：

- 脚本必须**显式校验自己的前提**：索引文件数明显偏小、或「缺文件」占比离谱时，直接把「根可能选错了」打出来，而不是列一堆缺文件让人猜。
- **打印要有上限**。上千条报错会把关键提示挤到屏幕外——先列前若干条，然后给出总数与提示。
- 多仓库工作区**始终显式给源码根**，别依赖自动探测。根可以给多个，按「从具体到宽泛」排序。
- 这条的通用版：**一个报错数量大到不合理的核验报告，先怀疑工具，再怀疑被检查的东西。**

### 21. 不要用「命令 + 管道」探测环境，先看文档

**现象**：花很多时间试哪些命令可用。

**怎么做**：环境的能力边界通常在项目约定文件（`AGENTS.md`、`CONTRIBUTING.md`、CI 配置）里写明。**先读它**，比试错快得多。CI 配置尤其可靠——它是「必须能跑通」的那份清单。
