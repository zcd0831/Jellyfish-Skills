# 阶段① 解析：怎么把一个陌生仓库读透

目标不是「读完」，是**攒出一份事实清单**——每条都带源码出处。这份清单是后面三个阶段的唯一输入。

顺序按下面的编号走。前四步是「先建地图再钻洞」，能避免最常见的低效：一上来就顺着目录逐个文件读。

---

## 1. 先跑起来，再读代码

没跑过就读架构，容易把设计问题想歪——你会以为某个约束是「设计缺陷」，实际是运行时约束逼出来的。

**做什么**：

- 按 README 把项目**真正构建并跑起来**（不是读它的构建说明）
- 跑通后立刻做几个「探针」实验，它们能用一分钟回答一堆猜测：
  - 不装可选组件时会发生什么？（→ 哪些能力是可插拔的）
  - 把一个配置项删掉、或写错类型，会怎样？（→ 校验在编译期还是运行期）
  - 只跑某一个子命令 / 子模块，能独立工作吗？（→ 边界划在哪）
  - 报错信息是谁打印的？（→ 错误处理在哪一层）

**产出**：一份「它长什么样」的直觉 + 几条能在本机复现的命令。这几条命令后面会原样写进文档的「上手」章节——**读者真正需要的是你自己验证过的那几条**。

**坑**：如果构建不起来，不要跳过这一步硬着头皮读。构建失败本身往往就是最有价值的知识（比如它其实依赖一个未被文档化的内部包）。把构建过程与失败原因如实写进文档。

---

## 2. 用构建文件画出模块地图

**构建文件是模块边界的唯一权威**，不是目录结构。目录可以随意分，依赖声明不会骗人。

按项目类型看：

| 生态 | 看什么 | 能得到 |
|---|---|---|
| JVM | `pom.xml` / `build.gradle` / `settings.gradle` | 模块列表、模块间依赖、版本、打包方式 |
| Node | `package.json` / `workspaces` / `pnpm-workspace.yaml` | 包边界、依赖、workspace 关系 |
| Go | `go.mod` / 目录即包 | 模块路径、第三方依赖 |
| Rust | `Cargo.toml` 的 `[workspace]` | crate 边界与依赖 |
| Python | `pyproject.toml` / `setup.py` / `setup.cfg` | 包边界、入口点（console_scripts） |
| 多语言 | 各子目录里各自的构建文件 | 真实的分层与语言边界 |

**必做的一件事**：检查**依赖方向是否单向**。如果构建文件层面声明了反向依赖或环形依赖，那就是文档里最值得写的一条（无论它是「刻意为之」还是「待还的债」）。

**产出**：模块依赖图。用 mermaid `flowchart TD` 画，边上标注依赖性质（编译期 / 运行期 / 反射注入）。这张图通常会成为首页的核心。

---

## 3. 找入口，而且要数清「有几个」

入口就是外壳。**同一套内核往往有多个入口**（CLI、HTTP 服务、GUI、库 API、定时任务）。把它们全找出来，你会立刻明白哪些是「同一件事的不同包装」，哪些真的分叉了。

怎么找入口：

- 构建文件里的 `main` / `Main-Class` / `console_scripts` / `bin` 字段
- 路由注册处（HTTP 框架的 router 定义）——它是「所有能力的一份索引」
- 命令注册处——同上，命令列表就是功能清单
- 依赖注入 / 装配层（见第 9 条）

**产出**：入口清单，每个入口一句话：「它把内核的哪些部分暴露给谁」。

---

## 4. 顺一条数据流读到底 ← 最关键的一步

**读这个仓库的正确单位不是「模块」，而是「一条数据流」。** 挑一条最能穿透所有模块的路径，从头读到尾。

怎么挑：**从用户的一个动作出发，到一次外部调用结束**。例如「用户敲了一行命令 → 解析 → 组装上下文 → 调用模型 → 执行工具 → 结果回灌 → 落盘」。

一条好的主干道具备：

- 起点在最外层（用户 / 请求），终点在最底层（网络 / 磁盘）
- 途径的每一站都是一个核心模块 —— 这样读它是**按需**的，天然形成优先级
- 能被你自己跑起来验证（承接第 1 步）

**怎么读这条路**：从入口函数开始，只追「下一步调用谁」，不要展开沿途的每个分支。追到终点后，再回头逐个展开你标记为「这里先跳过」的地方。

**为什么这样比逐个读文件好**：完整路径把「模块之间怎么对话」变成了具体代码，而模块清单只告诉你它们存在。读完主干道，你会发现所谓「架构」其实是几个函数调用。

**产出**：一张带注释的时序图或流程图 + 一条「每一站 = 哪个文件哪一行」的清单。这张图通常成为全书的骨干，各页围绕它展开。

---

## 5. 区分「契约清单」与「知识」

大项目里动辄上百个接口 / 类型定义 / DTO。**它们不是知识，是查询表。** 逐个读会耗尽全部预算，且读完记不住。

判据：**这个文件是否只声明「有什么」，而不解释「为什么」**。是的就归为清单。

清单的正确用法：

- 需要某个扩展点时，再去查那一页表
- 文档里**只写一张索引表**（名字 / 用途 / 一句话），不逐条展开
- 例外：**唯一的稳定契约**（插件作者 / 外部使用者必须依赖的那一层）值得单独一页，因为它的稳定性本身就是设计决策

**反面例子**（典型症状）：花两小时读完 `api/` 目录下 100 多个类，结果什么都没记住。这时间应该花在主干道上。

---

## 6. 挖注释里的「为什么」← 投入产出比最高

成熟仓库里知识密度最高的地方，是解释**「为什么不是另一种做法」**的注释。它们记录了作者踩过的坑，而这些信息在代码结构里看不出来。

**检索关键词**（中英各一套，直接 grep）：

```
中文：为什么 / 不能 / 必须 / 否则 / 而不是 / 注意 / 坑 / 尽量避免 / 故意 / 特例
英文：why not / cannot / must / otherwise / instead of / note that / caveat / careful /
      deliberately / intentionally / trade-off / workaround / revisit / TODO / FIXME / XXX
```

**怎么用这些注释**：它们天然是「设计依据」小节的内容。一段好的「为什么」注释，往往直接支撑一页里最值钱的那几段。

**产出**：把每条值得留的注释连同 `file:line` 记进事实清单，标注它解释了什么决策。

**另一个高价值来源：测试用例。** 测试是**行为规格**的可靠来源——「参数为 null 时抛异常」这种事实，从测试里读比从实现里推更准。搜 assert / 预期异常的测试，能快速得到边界行为清单。

---

## 7. 仓库自带的文档：当索引用，逐条回源码验证

README、约束文档、ADR、CHANGELOG、开发规范都在讲「该看哪」和「作者在意什么」，**是极好的索引用**。但它们会过时。

做法：

- 先读它们，拿一份「阅读地图」与「作者关注点清单」
- 每个要写进文档的论断，**回源码确认一次**
- 发现文档与源码不一致时：**以源码为准**，并把这个不一致本身记下来——那是文档里值得写的一条（读者最需要知道的就是「哪里和说明不一样」）

**注意**：如果仓库里有一份专门的「跨模块规则 / 约束」文档（解释「改坏了会静默出错」的那类），它的价值通常远高于行数暗示的——因为它筛过一遍。认真读它的章节结构，并在动笔前**主动查它**，而不是等被引用到才看。

## 8. 先量化规模，再决定精读 / 略读 / 跳过

动笔前先数一数，用数据分配预算：

```sh
# 文件数、总行数
find <root> -name '*.java' -not -path '*/test/*' | wc -l
# 最大的文件 Top 10（先看它们，但在读完主干道之后）
find <root> -name '*.java' | xargs wc -l | sort -rn | head -10
```

**分配原则**：

| 类别 | 投入 |
|---|---|
| 主干道经过的类 | 逐行精读 |
| 会静默失败的地方（见第 9 条） | 精读，至少读类注释 |
| 体积最大的类 | **不要因为它大就先读**——复杂度常常建立在别的概念之上，顺序错了很痛苦。先读它的类注释，正文用到再读 |
| 契约清单 / DTO / 生成代码 | 只读类注释，必要时查表 |
| 测试与构建脚本 | 抽样读，不逐行 |

**一条经验**：精读判据不是「文件大」，而是「**读错它会导致文档误导读者**」。

---

## 9. 优先读那些「出错时静默」的地方

有些地方的错误**没有任何界面提示**——测试照样过、日志里也没异常，只是行为偷偷变了。这类地方是文档最该覆盖的，也最容易被漏掉。

典型清单：

- **装配 / 依赖注入**：作用是「保证哪些实例必须唯一」。出错后果是两处代码看着对、用的是不同实例，故障现象诡异且不可复现。
- **并发与取消**：等待、超时、中断、清理。出错后是偶发的挂起或泄漏。
- **权限 / 安全策略的收敛方向**：组件故障时是拒绝还是放行。这个方向搞反了没有任何报错，只是不安全。
- **配置绑定与默认值**：缺字段 ≠ 显式给空值，类型不校验就会静默取默认值——「配置不生效」是最难排查的一类问题。
- **状态机的状态转移**：非法转移被静默忽略。
- **缓存的失效**：读到旧值。

读法：先读类注释（作者通常在这里写明了「为什么必须唯一 / 为什么必须拒绝」），再找**运行时校验代码**（启动自检、断言、fail-fast），校验代码的存在本身就是设计意图的证据。

---

## 10. 交叉验证，然后写事实清单

**一条论断至少要有两处来源**才算稳。三处更好：代码 + 测试 + 注释/文档。

交叉验证能抓出三类错误：
- 只有注释说「会校验」，代码其实没校验 → 文档若照抄注释就是错的
- 测试断言的边界与实现不符 → 说明有 bug 或有意为之，值得单独写
- 文档写的默认值与代码里的不一致

**事实清单的格式**（就这么简单，不要写成笔记）：

```
[ ] 论断（一句话，可证伪）
    依据：<相对路径>:<行号>  [+ 第二处依据]
    置信度：确认 / 待确认（写明缺什么）
    归属：拟写入哪一页
```

**为什么不用笔记**：写页时你要的是「能直接引用的断言」，不是「我读过这里」的感觉。清单里的每一行，最后都会变成文档里的一句 `file:line`。

**置信度是必须的字段**。写页时「待确认」的条目要么补读源码，要么在页面上明确标出来——**绝不允许把「待确认」悄悄写成肯定句**。

---

## 不该怎么读（反面清单）

- **顺着目录逐个文件读**：目录结构反映代码组织，不反映学习顺序。读到一半就迷失了。
- **从最小的模块开始读**：`api/`、`utils/`、`common/` 看起来「最基础」，其实全是清单，读完什么都不记得。
- **一开始就啃最复杂的那个文件**：它通常建立在多个概念之上（边界、缓存、状态机），顺序错了会很痛苦。
- **只读 README 就动笔**：那是转述，且会过时。读者自己也能读 README，不需要你转述。
- **把「读过的行数」当进度**：进度只有一个度量——**事实清单里「确认」条目的数量**。
- **遇到看不懂的就跳过并假设**：假设是文档最大的污染源。看不懂就标「待确认」，写页时要么补读、要么明说。
