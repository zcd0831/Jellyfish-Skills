# 阶段② 设计：切页、排序、定页面契约

输入是阶段①的事实清单，输出是一份**页面契约**：每个页面的编号、标题、主题、覆盖哪些源码、以及每页必须有哪些构件。

---

## 1. 先定读者，再定深度

同一份代码，对「使用者」和「改造者」是两份完全不同的文档。

先把这句话写下来（它会成为首页的开头，也会成为后面每个取舍的判据）：

> **读者读完这套文档，能做什么？**

两种典型答案，对应完全不同的切法：

| 读者 | 读完能做什么 | 主体内容 |
|---|---|---|
| 使用者 / 集成方 | 会配置、会用、会排查 | 能力清单、配置、扩展点、常见故障 |
| 改造者 / 贡献者 | 能安全地改一处代码而知道会波及什么 | 数据流、状态与生命周期、约束与不变量、静默失败点 |

**同时服务两类读者时**：让「改造者」的内容当主体（它包含使用所需的机制），把「使用者」的内容压成前面的上手页 + 后面的参考页。不要试图每页都兼顾两者，那会让每页都冗长。

---

## 2. 按依赖顺序切页，不按目录切

**这是整套设计里最重要的一条。**

目录结构反映的是「代码怎么放的」（同等地位的文件放一起），学习顺序反映的是「概念依赖谁」。两者经常不同。

切页判据（三条同时满足才算一页）：

1. **一页一个主问题**，且能用一个标题说清（「XX 是怎么实现的」）
2. **读者读到这一页时，所需的前置概念都已经出现过** —— 否则说明页码排错了，或者该拆成两页
3. **这一页不是目录的转写** —— 如果一页的内容只是「把 `foo/` 目录下的文件逐个介绍一遍」，那是转写，不是知识。合并它，或者按「概念」重新组织

**怎么排顺序**：拿阶段①的那张主干道图，把每条边展开成一页或几页。天然的排序是：

```
整体是什么 → 怎么跑起来 → 全局结构（模块图）
  → 主干道上的每一站（按调用顺序）→ 外壳与对外接口
  → 扩展机制 → 工程实践（测试/构建/发布）→ 参考（FAQ/术语/坑点清单）
```

---

## 3. 分部分（Part）的默认骨架

中大型项目用五部分基本都合适，可以按需增删：

| 部分 | 内容 | 判据 |
|---|---|---|
| 一、入门 | 项目是什么 / 怎么跑 / 全局结构 | 读完能跑起来并说出它由哪几块组成 |
| 二、核心机制 | 主干道上的每一站 | 读完能不看文档复述主干道 |
| 三、外壳与接口 | CLI / HTTP / UI / 库 API | 读完知道能力怎么暴露出去 |
| 四、扩展机制 | 插件 / SPI / 事件 / 钩子 | 读完能写一个扩展 |
| 五、工程与参考 | 测试构建 / 坑点 / 对比 / FAQ 术语 / 阅读路径 | 工具书性质，按需查阅，可跳读 |

**为什么把「坑点」单独成页**：坑点是**横向**知识（跨越所有模块），塞进任何一页都会打断该页的叙述，而散落各处又查不到。单独一页、按主题分组，是最有用的形态。

**「对比」与「FAQ/术语」也值得单独成页**：它们服务「查阅」而非「顺序阅读」，混进正文会拖慢主线。

## 4. 页数控制

- 一页 = **1 个主问题 + 3~6 个子问题**。少于 3 个子问题，说明这页太碎（导航成本 > 阅读成本）；多于 6 个，说明该拆。
- **总页数的合理区间**：小项目 8~15 页，中型 20~40 页，大型 40~80 页。低于 8 页通常说明文档写成了 README。
- **单页 HTML 的舒服区间是 300~800 行**（含标记）。超过 1000 行读者会在中途放弃；低于 200 行说明没讲透。
- **不要为了页数好看而强行拆**。判断标准始终是「这个概念单元能否独立成篇、且前置条件齐备」。

## 5. 编号与命名约定

```
NN-<slug>.html          内容页：NN 是两位十进制编号，从 01 开始
index.html              首页，编号 00（即「第 0 页」）
assets/                 静态资产（style.css / app.js / 可选的 vendor/）
```

**`assets/` 里放什么、不放什么**：

| 文件 | 怎么来 | 进版本库吗 |
|---|---|---|
| `style.css` `app.js` | 从本技能 `templates/` 复制一份，复制后就是产出仓库的资产 | 是 |
| `vendor/highlight.min.js` `vendor/mermaid.min.js` | 需要完全离线时自己放进去 | **否** |
| `verify-refs.sh` `check-docs.py` | **不放这里**，从本技能 `scripts/` 直接调用 | — |

第三方库不入库的理由：它们是别人编译好的 minified 构建产物、约 3.4 MB，而且**对文档不是必需品**
——缺库时 `app.js` 先回退 CDN，再不行就降级（代码不着色、图以源码形式展示并给出提示），页面照样能读。
它们也**不内联进页面**：`mermaid.min.js` 一份 2.9 MB，塞进 30 个页面就是每页 3 MB，
打开变慢、diff 不可读。放本地时**版本必须与 `app.js` 里 CDN 兜底用的版本一致**，
否则会出现「本地渲染与联网渲染不一样」这种最难查的差异。

核验脚本不进产出目录的理由在 `SKILL.md`「复用优先于重建」：两份副本必然漂移。
顺带一提，`check-docs.py` 把「引用了 `vendor/` 下的文件、但该文件不存在」当作**警告而不是错误**
——库本来就是按需获取的。

**约定要一次定死，后面全会依赖它**：

| 约定 | 例 | 为什么 |
|---|---|---|
| 页内图 / 表编号带页号 | `图 03-2`、`表 07-1` | 跨页引用唯一；也能一眼看出「引用的是哪一页」 |
| 引用别的页面用 `NN 页` | 「详见 `12 页`」 | 比标题短，且页号稳定（标题会改） |
| 链接文字以页号开头 | `<a href="03-architecture.html">03 整体架构</a>` | 侧栏、正文、翻页三处能自动核对一致性（脚本可查） |
| 每个页面自己的编号出现在三处 | `<title>` / `<h1>` / 面包屑 | 同上，脚本可核对 |

**这四条约定不是洁癖，是为了让核验脚本能自动查错**。人眼维护 30 个页面的编号一致性必然出错（见 `04-verification.md`）。

## 6. 页面契约：每页必须有的构件

**顺序固定，构件齐全**。缺哪一件，读者就会在某个环节卡住。

| # | 构件 | 作用 | 必需 |
|---|---|---|---|
| 1 | 顶栏：品牌链接 + 搜索框 | 全站定位 | 是 |
| 2 | 侧栏：完整页面目录，按部分分组，当前页高亮 | 全站导航 | 是 |
| 3 | 面包屑 | 我在哪 | 是 |
| 4 | `<h1>` 页号 + 标题 | 我在哪 | 是 |
| 5 | 一句话副标题（`page-sub`） | **读者 3 秒内决定要不要读这页** | 是 |
| 6 | 学习目标（3~5 条，「读完能做什么」） | 建立预期，也是自测标准 | 是 |
| 7 | 正文小节：每节 = 结论 → `file:line` 出处 → 15~30 行代码 → 表格/图 → 设计依据 | 知识主体 | 是 |
| 8 | 设计依据块（`callout design`） | **本文档区别于普通文档的核心**：为什么这样而不是那样 | 是（每页至少 1 个） |
| 9 | 坑点块（`callout pitfall`） | 哪里容易踩、出错现象是什么 | 建议（每页 0~3 个） |
| 10 | 危险提示（`callout warn`） | 会造成数据损坏 / 安全问题的操作 | 按需 |
| 11 | 经验提示（`callout tip`） | 省时间的技巧 | 按需 |
| 12 | 关键结论（编号列表，可独立阅读） | 只读这一段的读者也能拿到要点 | 是 |
| 13 | 翻页（上一页 / 下一页） | 顺序阅读 | 是 |
| 14 | 页脚：本页依据 | 说明这页的结论建立在哪些材料上 | 是 |
| 15 | 脚本引用（3 行） | 高亮 + 图表 + 交互 | 是 |

**为什么这 15 件都要**：把它们连起来读一遍——**它们构成了一个完整的阅读闭环**：我在哪 → 值不值得读 → 会学到什么 → 凭什么这么说 → 为什么这么设计 → 有什么坑 → 结论是什么 → 下一步去哪。

少任何一件，闭环就断在那一处。

**为什么「设计依据」是核心**：代码本身、测试、README 都能回答「是什么」，只有「为什么这样而不是那样」需要有人把散落各处的证据（注释、提交历史、约束文档、代码里的取舍痕迹）综合起来。**这才是这套文档存在的理由**——否则读者读代码就够了。

## 7. 代码块的呈现约定

每个「讲代码」的小节按同一套顺序展开，读者很快会习惯：

```
① 结论先行：一句话说这节在讲什么
② 出处行：<div class="src-block">path/to/File.ext:120-145</div>
③ 代码：<pre><code class="language-xxx"> 15~30 行，逐字复制
④ 逐点解读：表格（步 / 做什么 / 要点），把代码里的每一步对上
⑤ 设计依据：为什么不是另一种写法
```

**为什么「出处行」单独成一个构件**：读者常常想自己去看完整上下文。把路径和行号放在代码**上方**且样式上明显区分，他可以直接复制去编辑器里跳。放在代码块里当注释会被复制走，放在下方则要回头找。

## 8. 首页（index）的职责

首页不是「文档列表」，它是**全书的锚点**。必须包含：

1. 一句话说明这套文档是什么、给谁看
2. **关键事实表**：规模（模块数 / 行数）、技术栈版本、外部依赖、规模最大的几个组件 —— 都带出处
3. **全局结构图**（模块依赖 / 分层图）：一眼看懂它由哪几块组成、依赖方向如何
4. **页面地图**：按部分分组的卡片，每张卡片 = 页号 + 标题 + 一句话摘要 + 本页覆盖的源码文件
5. **推荐阅读顺序**：不同目的的读者走哪条路（「只想用」/「想改内核」/「想写扩展」）
6. 文档自身的说明：如何离线阅读、怎么更新、核验脚本怎么跑

**卡片上的「覆盖的源码文件」这一行很关键**：它让读者能从「我知道的那个文件」反向找到「该读哪一页」。

## 9. 多页 vs 单页：怎么选

| 情形 | 选择 |
|---|---|
| 内容能在 2~3 屏内讲完 | **单页**就够了，不要拆 |
| 需要顺序阅读、有前置概念依赖 | **多页**（本文档的形态） |
| 主要用途是查阅、条目化 | 单页 + 强目录，或者按条目分页 |
| 需要打印 / 分享给别人 | 多页各自可独立阅读更友好 |

**多页的代价**要认：导航必须在每页重复（侧栏），一致性要靠脚本维护，编号会随插页变得麻烦（见 `05-pitfalls.md`）。

**好处**：每个页面可以有自己的学习目标与结论；链接可以精确指向「第 3 节」；读者能分次读完。

## 10. 接进目标仓库已有的文档体系

不要另立平行世界。定页之前先看：

- 仓库已有的文档放在哪？用什么格式（Markdown / 静态站点 / Wiki）？**新文档放在它惯常的位置**，或放在它已经在用的文档目录下的子目录。
- 有没有既有的样式与导航体系？有就复用，别另起一套 CSS。
- 命名风格跟它现有的一致（`kebab-case` 还是 `snake_case`？前缀是编号还是日期？）
- 仓库的贡献规范（`CONTRIBUTING.md` / `AGENTS.md` 之类）里有没有对文档的要求？**照做**。

**唯一的例外**：如果要做的东西与既有体系性质不同（比如既有的是「使用手册」，你要做的是「源码解析」），那就**明确分开目录**，并在两边的入口互相指一下，让读者知道该去哪个。
