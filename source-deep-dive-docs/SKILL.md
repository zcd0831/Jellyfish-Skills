# 源码深度解析 → HTML 学习文档

一套工序，产出是**一套自包含的多页 HTML 文档**：每个页面讲透一个概念单元，页间可互跳，双击就能离线阅读。

工序分四阶段，顺序不能颠倒——**解析不足就动笔，写出来的必然是从注释和 README 里抄来的东西**，那是转述，不是解析。

```
① 解析 ──→ ② 设计 ──→ ③ 撰写 ──→ ④ 核验
读源码      切页与排序    逐页落笔      逐条回源码
出「事实清单」  出「页面契约」  出 HTML     出核验报告
                ↑                              │
                └──────── 不通过就回炉 ─────────┘
```

## 什么时候用 / 不用

**用**：目标仓库有一定规模（≥ 几千行、≥ 数个模块），读者需要理解**设计意图与取舍**——为什么这样而不是那样，哪里改坏了会静默出错。

**不用**：

| 你的目标 | 该用的做法 |
|---|---|
| 写安装 / 使用说明 | 一份 README，不需要多页 HTML |
| 写 API 参考 | 由签名自动生成，人写的会过时 |
| 读懂一个单文件脚本 | 直接读，不需要工序 |
| 只想快速了解某个项目 | 读它自己的 README 与架构图 |

判断标准：**如果全部内容都能由「读代码表面」得到，就不需要这套工序**。这套工序的价值在于把「代码里没写、但只有读代码才能推出来的东西」写出来。

## 产出物

```
<输出目录>/
  index.html                 # 首页：总览 + 页面地图 + 全局图 + 推荐阅读顺序
  01-<slug>.html             # 每个概念单元一页，文件名带两位编号
  02-<slug>.html
  ...
  assets/
    style.css                # 一份，全站共用
    app.js                   # 一份，全站共用（导航/搜索/高亮/图表/行锚点）
    vendor/                  # 可选：第三方前端库（本地优先 + CDN 兜底），不入版本库
```

产出目录里**只有页面和前端资产**。两类东西刻意不进去：核验脚本一律从本技能 `scripts/` 调用，
第三方前端库放不放 `assets/vendor/` 由读者自己决定（缺了会自动回退 CDN）。理由见「复用优先于重建」。

## 四阶段工序

| 阶段 | 目标 | 产出（下一页的输入） | 详细做法 |
|---|---|---|---|
| ① 解析 | 让每条论断都有源码出处 | **事实清单**：`论断 / 依据 file:line / 置信度` | `references/01-reading-source.md` |
| ② 设计 | 定读者、切页、定顺序 | **页面契约**：页号 / 标题 / 主题 / 覆盖的源码 | `references/02-doc-architecture.md` |
| ③ 撰写 | 把事实清单写成页 | 每页 HTML | `references/03-page-authoring.md` |
| ④ 核验 | 证明引用与结构都对 | 核验报告（零缺文件、零越界） | `references/04-verification.md` |

**逐阶段的验收点**（不通过不要往下走）：

- ① → ②：能不能不看笔记，画出「一条从入口到一次外部调用的完整路径」？不能就是没读透。
- ② → ③：每页的「前置概念」是否都已经在更早的页面里出现过？有没有页面是「目录的转写」而不是「概念的切分」？
- ③ → ④：每页是否都挂了 ≥ 10 处 `file:line`？随手抽 3 处能否立刻定位到源码？
- ④：核验脚本退出码是否为 0？

## 五条红线

1. **每条事实都要能指出位置**。写完一句论断，反问「这句的依据是哪一行」。答不出来就删掉或标 `<待确认>`。禁止凭函数名推测行为。
2. **引用即逐字复制**，15–30 行，从源码原样粘贴。不要「整理一下」——整理过就不再是证据，且行号会对不上。
3. **不编造**。API、配置项、默认值、错误行为、性能数字，一律回源码确认；确认不了就写「未在源码中找到」。
4. **敏感信息脱敏**。密钥、token、密码、真实内网地址、个人路径一律换成 `<YOUR_API_KEY>` 之类占位符再写进文档。
5. **交付前必须跑核验脚本**，且这是硬性门槛，不是建议：`verify-refs.sh` 与 `check-docs.py` 都要通过。**「看起来没问题」不算通过。**

## 复用优先于重建

目标仓库里**已有**同类资产时（样式表、脚本、引用核验工具、文档骨架），先复用它，不要另起一套——两套资产必然漂移。

本技能的 `templates/` 与 `scripts/` 是**参考实现**，但两者的去向不同：

- `templates/`（页面骨架、`style.css`、`app.js`）：目标是「从零起一套」，或者「已有资产明显更差」时才复制过去。复制之后它就是目标仓库的资产，要随仓库一起版本管理。
- `scripts/`（核验脚本）：**永远不复制进产出目录**，一律从本技能目录调用。复制过去立刻变成两份会各自漂移的副本——核验脚本的价值全在「跑的就是最新那一版」，而文档仓库里那份没人会去同步它。
- 第三方前端库（`assets/vendor/`）：**不进版本库**。它们是别人编译好的 minified 构建产物、体积以 MB 计，而缺库时 `app.js` 已经能回退 CDN、能降级。放什么、放哪里见 `references/02-doc-architecture.md`「`assets/` 里放什么、不放什么」。

同理，**目标仓库已有的文档体系要接进去**，不要另立一个平行世界：文档放在它惯常的位置，文件命名跟它现有风格。

## 可移植性提醒

工序是与语言、框架、仓库规模无关的，但有三处要按目标仓库替换：

- **引用核验脚本的文件扩展名**（默认覆盖常见十几种语言，`verify-refs.sh` 顶部可改）
- **源码根的探测方式**（默认按 `.git` 与常见构建文件向上查找，多仓库工作区用参数显式给）
- **前端资产**（`style.css` / `app.js` 是纯静态、无构建依赖的通用实现，直接可用；若目标仓库有自己的文档站点技术栈，优先用它）

## 验收标准（Definition of Done）

- [ ] `sh <技能目录>/scripts/verify-refs.sh <输出目录> <源码根...>` 退出码 0：**零缺文件、零越界**；「歧义」逐条修掉
      （`<技能目录>` = 本 SKILL.md 所在目录；两个位置参数都给上，别依赖自动探测；
       多仓库工作区必须显式给源码根，见 `references/04-verification.md`；选错根的症状是「索引文件数很小 + 缺文件上千条」）
- [ ] `python3 <技能目录>/scripts/check-docs.py <输出目录>` 退出码 0：编号、侧栏、翻页、链接全部一致
- [ ] 抽 10% 的引用人工回源码复查：**行号对，内容也要对**（脚本查不出「行号对但引错段落」）
- [ ] 断网双击 `index.html`：能读、能跳转、图有降级显示、代码有行号
- [ ] 每个页面都有：一句话副标题、学习目标、`file:line` 出处、至少一张图或表、设计依据、关键结论、上下页导航
- [ ] 文档里的密钥/内网地址已脱敏
- [ ] 实测过产物**能打开并能用**——静态检查通过 ≠ 能跑（见 `05-pitfalls.md` 第 9 条）

## 常见坑（完整清单见 `05-pitfalls.md`）

1. **批量改编号会互相碰撞**（旧号恰好是新号），必须两段式 + 占位符，且规则有先后顺序。
2. **引用同名文件会歧义**，核验脚本要报歧义而不是静默取第一个。
3. **前端库选错包**：给打包器用的 CommonJS 版本在浏览器里直接报错，必须实跑验证。
4. **本地优先与 CDN 兜底要分别验证**：只测一条路，另一条坏了也不知道。
5. **`file://` 下 `fetch` 会被拦**，任何「JS 注入导航」的方案都要换成内联。
6. **核验脚本一复制就会漂移**：产出目录与技能目录各留一份，改的永远是技能里那份。脚本只从技能目录调用，产出目录里一个都不留。
