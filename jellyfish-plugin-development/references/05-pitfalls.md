# 坑点清单

按「症状 → 机制 → 怎么避」写。**症状是你在现场会看到的东西**，机制用来判断是不是同一个病。

## 一、照抄文档写不出来

| # | 症状 | 机制 | 怎么避 |
|---|---|---|---|
| 1 | 照 README 的骨架写，编译报「第 4 个参数类型不对」 | 文档里的 `ToolDescriptor(name, description, parametersSchema, /* order */ 0)` 是旧签名；现在的第 4 个参数是**必填参数名列表**（`List<String>`），`order` 在 `RegisterOptions` 里 | 签名以 `<kernel>/jellyfish-api/.../extension/` 下的源码为准；本文档的模板是按源码写的 |
| 2 | 插件 jar 一装上去就被拒 / 报 `ClassCastException` / 内核加字段后新字段读不到 | 插件 jar 里带了 `zcd/jellyfish/api/` 或 `org/pf4j/` 的类：PF4J 插件类加载器子优先，会把父加载器那一份遮蔽成两个互不相识的类型；内核加载期直接拒绝这种 jar | `jellyfish-api` 依赖写 `provided`；shade 的 `includes` 里绝不出现 api / pf4j / slf4j；交付前跑 `scripts/check-plugin-jar.sh` |
| 3 | 「我明明改了内核/插件，行为却没变」；升级内核后一堆 `NoSuchMethodError` | 增量编译复用了按旧 api 编出的 `target/`，编译问题被伪装成运行期问题 | **每次打包都 `mvn -q clean package`** |
| 4 | 单测全绿，但插件就是没生效 | 描述符少键 / `plugin.class` 不对这类问题在描述符体检阶段被记成 loadError，插件被**静默跳过**（内核照常启动） | 加一条「加载链路」用例（真实描述符 → 断言状态 `STARTED`）；验收时看启动日志里那句 `插件运行时已启动` |
| 5 | 装了插件以后，**别的**插件也没装上 | `plugin.class` 不满足「实现 `JellyfishPlugin` + 非抽象 + 公开无参构造器」时抛的不是 `PluginRuntimeException`，会中断该次加载 | 入口类 `public final` + 显式公开无参构造器（别让它依赖构造器注入） |
| 6 | 插件启动失败，报 `DUPLICATE_HANDLER` | 带路由键的点（工具名 / 命令名 / 标记字符 / provider 名）**同键至多一个**；两个插件抢同一个名字会在启动期暴露 | 工具名加自己的前缀；确实要顶替就用 `RegisterOptions.override(true)`（压链顶，可回退） |

## 二、注册了却没生效 / 生效得不对

| # | 症状 | 机制 | 怎么避 |
|---|---|---|---|
| 7 | 注册了贡献，但内核像没看见 | 类型级贡献的合并规则**在调用点**，不同点不一样：链式（`input_transform`、`tool_argument_pre`、`tool_result_post`）、逐字段取 `order` 最小且表态者（`request_tuning`、`aging_strategy`、`compaction`）、每插件至多一块（面板 / 状态栏） | 按 `01-requirement.md` 的表核对；多插件场景下把 `order` 写清楚 |
| 8 | 「不表态」写成了空字符串 / 空集合，结果行为变了 | 每个点的「不表态」是不同的：`empty()` / `none()` / `abstain()` / `proceed()` / 返回 `null` | 用对应结果类提供的工厂，别自己拼一个空对象 |
| 9 | 想「放行」某个工具，却发现权限扩展点里根本没有 allow | `PermissionVerdict` 只有 `abstain` / `ask` / `deny`：插件只能**收紧**，放行是内核核心策略的事 | 判断「不关我事」就返回 `abstain()` |
| 10 | 权限拦截里读配置失败，结果所有工具都被拒了 | 拦截处理器**抛异常或返回 `null` 一律按拒绝**（fail-closed，有意为之） | 把「判不出来」与「该拒绝」分开表达；配置错误在启动期就抛出来 |
| 11 | 界面一卡一卡，或点开面板就卡死 | 面板 / 状态栏 / 渲染提示 / 输入补全 / 输入标记解析都跑在**渲染线程、没有超时** | 这些处理器只读内存、立刻返回；联网与子进程放到另一个脚本里（范例：`stock` 取数 + `stockpanel` 只读缓存） |
| 12 | 界面开始无限重画 | UI 贡献处理器里发了 `UiInvalidatedEvent` → 「失效 → 收集 → 失效」死循环 | 在 UI 处理器里不要发这个事件；要被动刷新就让真正改数据的那一方发 |
| 13 | 事件处理器里的异常没人看见 / 事件丢了 | 事件是旁路且**可丢**（网关没起、队列满、worker 忙都会丢）；订阅者的异常只记 WARN | 事件只做通知与统计；**必须到达**的结果用工具返回值 / 命令输出传递 |
| 14 | 用 `present` 推的通知丢了，重试又更乱 | `present` 是**可丢**的展示数据（每个 owner 有界，满即丢最新） | 不把它当失败判据、不重试；关键状态让外壳来**拉**（面板 / 状态栏） |

## 三、脚本插件

| # | 症状 | 机制 | 怎么避 |
|---|---|---|---|
| 15 | 调用报「清单与实现不一致」，该脚本全部调用失败 | worker 冷启动时按**名字集合**比对清单与装饰器声明；缺省 `manifestStrict=true` → 拒绝服务 | 改完脚本跑 `dump_manifest.py --write`；交付前 `--check` |
| 16 | 模型按错误的参数调用我的工具，而代码里写的是对的 | **描述与参数只在清单里**决定模型看到什么（比对只比名字，不比内容） | 清单是工具定义的唯一来源；改描述去改清单 |
| 17 | `--write` 之后清单是空的 | 用 shell 重定向（`> manifest.json`）时 shell 先把文件截空，而生成器要读它确认入口文件名 | 用 `--write`，不要重定向 |
| 18 | 脚本失败被当成成功，模型以为一切正常 | 返回 `{"error": ...}` 是**正常输出** | 失败一律 `raise ScriptError(...)` / `throw new ScriptError(...)` |
| 19 | 只写了 `request_tuning` / `aging_strategy` 贡献，脚本却从来没被拉起 | 热路径点**不冷启动**：worker 没热着就返回「不表态」 | 至少再提供一个真会被调用的点（工具 / 命令 / `turn_context` / `turn_before`…） |
| 20 | 面板里做的联网取数，把界面卡住了 | 面板处理器跑在渲染线程且没有超时，而脚本调用是一次进程往返 | 拆成两个脚本：一个取数、一个只读缓存画面板 |
| 21 | 配置里写了 `${MY_KEY}`，插件整个起不来 | `${ENV}` 是**硬失败**：变量没设就「启动即失败」，不是取不到就留空 | 真用的密钥才写 `${...}`，否则留空字符串 |
| 22 | 脚本读不到环境里的密钥 / 依赖找不到 | 脚本进程的环境是**严格白名单**（密钥不在其中；`PYTHONPATH` / `NODE_PATH` / `VIRTUAL_ENV` 在白名单里） | 密钥走 `scripts.<脚本 id>` 配置段；依赖装在脚本自己的环境里 |
| 23 | 脚本读写文件跑到了奇怪的地方 | 相对路径按**宿主进程的工作目录**解析 | 用 `__file__` / `__dirname` 定位脚本自己的目录 |
| 24 | 命令的候选查询里干了写入 / 很慢，界面发卡 | 候选查询是**只读且必须快**的那条路；那一次 `tokens` 是 `None`（Node `null`） | 候选查询单独写一个函数；`tokens == []` 是「执行且没带参数」，与 `None` 不是一回事 |
| 25 | 周期任务跑几次就静默不跑了，或每次报一条 WARN | 任务体的异常会被记 WARN 并计入熔断；「这次跳过」应当是正常 `return` | 任务体自己容错（跳过用 `return`）；成功后桥接层会代发界面失效，不用自己发 |
| 26 | 关掉自动刷新后仍有 python 进程常驻 | 周期任务本身不会因为开关而停（清单里的 `schedules` 在启动期就定了） | 要连进程一起去掉：删 `schedules`、移走脚本目录，或停用整只桥接插件 |
| 27 | 改完 `manifest.json` 不生效 | 清单在桥接插件**启动期**读入 | 改清单必须重启进程；只改入口实现等 worker 冷启动（空闲 300 秒自毁）即可 |
| 28 | Node 里 `await` 了事件处理器，却发现它没被等 | 工具 / 命令 / 贡献的 handler 会被 `await`，**事件处理器不会**（事件是旁路） | 事件处理器别承担后续请求依赖的副作用 |

## 四、架构边界（不是 bug，是设计）

| # | 现象 | 说明 |
|---|---|---|
| 29 | 插件里拿不到 `sessionId` / `cwd` / 会话列表 | `PluginContext` 与 `RuntimeInfo` 刻意不给；工具的相对路径按进程 cwd 解析 |
| 30 | 想「替用户说一句话」或起一轮对话，找不到入口 | 插件不能新开会话、不能起回合；Java 侧最多 `submit(PluginAction)`（五种动作之一）；命令可以用 `CommandResult.handoff` 声明「把这段文本当作我的输入继续跑」 |
| 31 | 想给插件自己的公告栏 / 通知，找不到通道 | 往外壳说话只走 `PluginContext.present` + 发布 `PluginNotificationEvent`；**不要新建通道**（状态一律让外壳来拉） |
| 32 | 想让自己的工具进 plan 模式的只读名单，结果进不去 | `ToolDescriptor` 里没有「只读」字段（曾有过，已移除）：只读与否**完全由用户配置**决定 | 
| 33 | 测试夹具用静态工厂构造 api 值类型，改名 / 加字段后数据静默丢失 | 跨边界值类型「恰好一个可见构造器 + 静态工厂」，新增字段只能用新静态工厂补；**夹具必须用全字段构造器**，否则「后加字段读不回来」会被吞掉 | 
| 34 | 插件加载失败，但内核照常启动，用户察觉不到 | 这是有意的：坏插件不该拖垮内核。因此「没生效」比「报错」常见得多 | 

## 遇到诡异现象怎么查（先分类，再定位）

| 现象 | 先查什么 |
|---|---|
| **没生效**（命令不在 `/help`、工具调不到、面板不出现） | ① jar / 脚本目录在不在扫描目录下（roots 只扫下一层）；② 有没有被 `plugins.disabled` / `plugins.enabled` 排掉；③ 启动日志里针对你插件的 error 行；④ 脚本侧敲 `/python` / `/node` 看台账的「问题」段 |
| **生效了但行为不对** | ① 是不是「不表态」写错了（空对象 vs `abstain()`）；② 多插件同点的合并规则与 `order`；③ 清单里的描述 / 参数（模型按清单调，不按你的代码）；④ 是不是在渲染线程做了慢活 |
| **装完就崩 / 调用就崩** | ① jar 里有没有自带 api（`check-plugin-jar.sh`）；② `mvn clean` 了没有；③ 插件 `stop()` 之后是否还有后台线程在注册；④ 脚本侧看熔断状态与 worker pid 是否在变 |
